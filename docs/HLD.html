1. Scope and invariants

The service accepts synthetic telecom alarms through Spring MVC, persists every unique accepted event using JPA/PostgreSQL, and maintains a separate active-state projection. RAISED creates or updates an active key; CLEARED removes it. Unknown clears fail with 409. Exact event replay returns the original ID without changing state; conflicting ID reuse fails.

Atomic acceptance: history, duplicate receipt and active projection commit or roll back together. No event is acknowledged as new before commit. Notification delivery is optional in the assignment and remains unimplemented.

V2 closes seven gaps: fractional timestamps, cross-element contention, slow uploads/admission, shifting pagination, permanent error classification, storage growth and failure-test coverage. Existing V1 database content is migrated without dropping alarm data.

3. Exact-key concurrency across instances

Each ingestion transaction first locks event:EVENT_ID, then element:ELEMENT_ID. Lock rows are inserted with ON CONFLICT DO NOTHING and acquired with SELECT FOR UPDATE. The order is consistent and locks remain held until commit/rollback. Duplicate replays stop after the event lock. These are exact string keys, so unrelated elements do not share hash stripes or a global ingestion mutex.

The event lock protects global uniqueness even if competing requests identify different elements. The element lock protects missing-state insertion, repeated raises, competing clears and raise-versus-clear races. History and active-key unique constraints provide database backstops. The connection pool and request admission still bound overall capacity; a flood can exhaust them even though a single blocked element no longer serializes all writers.

Acceptance order is processing order per element, not producer time or socket arrival. Late timestamps are metadata and still take effect. Global IDs express allocation order, not cross-element commit order. Read snapshots freeze the committed rows observed by one SELECT. Application restarts preserve state, receipts and snapshots in PostgreSQL.

Upgrade boundary: stop all V1 writers before starting V2. Their different locking protocols cannot safely overlap. Multiple V2 instances can share the database and archive storage.

4. Query consistency

A first list request materializes matching AlarmView payloads into a database snapshot with a random UUID token and expiry. All pages slice that same payload, so content and total count cannot drift under concurrent inserts, clears or archival. Another application replica can serve the next page. The response preserves content/page/size/totalElements and adds snapshotId/expiresAt.

Page >0 requires the token. Expired or unavailable snapshots return 410; a token used on a different endpoint/filter returns 400. Refreshing current state requires a new snapshot. Defaults: 120 seconds, 32 snapshots, 10,000 records and 4 MiB each. Oversize queries return 413 and exhausted snapshot admission returns 429. A maintenance-only singleton serializes quota checks; it is not used by ingestion.

5. Retention without losing event identity

After 30 days of server acceptance age, inactive event payloads are exported in batches of 500 to GZIP JSON Lines. History referenced by active state is retained. The exporter fsyncs and atomically publishes the file before deleting database rows. Receipt backfill and deletion share event locks with ingestion, including legacy V1 events.

A receipt permanently stores the event ID, original history ID and canonical SHA-256 payload fingerprint. It recognizes exact replay after archival without reactivating state. Archives preserve full payloads. Filesystem failure or full archive capacity keeps database rows and logs an operator-action error. A crash after publication and before transaction commit can duplicate an export; readers deduplicate by event ID.

Default archive limits are 1 GiB and 10,000 files. A lifetime generated-ID ceiling of 10,000,000 bounds history/receipt/lock cardinality without a global transactional counter. An attempted ID above the ceiling returns 507 and rolls back. Rollbacks consume sequence values, so capacity is conservative. Replays remain available at capacity. Operators must size, back up and deliberately increase capacity; unlimited permanent deduplication cannot consume finite storage forever.

6. Security and availability controls

JSON parsing rejects unknown/duplicate fields, trailing content, numeric enums, coercions and fractional timestamps. Identifiers use constrained ASCII syntax; descriptions have a length bound and reject NUL. Bodies are capped at 16 KiB. Parameterized SQL prevents values from becoming executable SQL. Problem responses and application failure logs omit raw payloads, credentials and SQL.

Per process: 32 admitted requests, 30 requests/second per socket peer with burst 120, and at most 1,024 peer buckets. Forwarded headers are not trusted. A five-second upload budget plus Tomcat blocking-read timeout bounds slow clients; one final read can extend the budget by one idle interval. 429 and 408 explicitly signal rejected work.

Only the API is published on host loopback; PostgreSQL is Docker-internal. The container runs unprivileged and archives use a persistent writable volume. Authentication, authorization and TLS remain deployment work for public exposure; admission is per replica and does not replace authenticated distributed ingress controls.

8. Verification and remaining scope

Automated tests execute real Spring validation, migrations and transactions against H2 and an optional disposable PostgreSQL database. They cover lifecycle and concurrency plus stable snapshots, quotas, archival/replay, filesystem failure, rate admission and error classification. The reusable Python end-to-end harness starts two JVMs and checks HTTP → database → response, blocked-element isolation, lost responses, application kill during insertion, optional immediate database restart, scheduled archives, slow sockets and burst overload.

Executed versions, counts and results are recorded in validation evidence. The harness creates a fresh alarm_e2e_* database and refuses occupied test ports. It does not target the user's running API. Notification delivery, sustained telecom-scale load testing, authentication, observability and backup restoration remain outside the implemented scope.
