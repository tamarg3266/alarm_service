Telecom Alarm Service
High-Level Design

A Spring Boot backend that accepts synthetic network alarm events, maintains durable active state, preserves event identity across retries and archival, and serves stable paginated queries.

01 | Scope and architectural goals

The delivered application is a REST backend for simulated telecom alarms. An alarm is identified by (elementId, alarmCode). Each unique accepted event is recorded in history and either creates, updates or clears that alarm's active state. Read APIs expose active alarms, alarms for one element, retained history and active severity counts.

The design prioritizes transactional correctness, repeatable retries, explicit resource bounds and clear operational failures. PostgreSQL is the production source of truth. There is no separate in-memory alarm cache and no frontend included in this backend repository.

Core invariant: a newly accepted event's history, permanent duplicate receipt and active-state transition commit together. A replay or rejected request must not append another accepted event or change active state.

Filtered history, frozen query snapshots, archive-before-delete retention and multi-instance ingestion coordination are implemented. Asynchronous external HTTP notifications remain outside the delivered scope.

Separation of responsibilities

The controller owns routing and response adaptation; the application service owns business decisions. Entities model history and active state. Input uses a validated immutable record; output uses an explicit response DTO. Constructor injection exposes dependencies, while repository contracts isolate persistence operations.

This is a pragmatic layered design. Entities retain JPA annotations, application methods use Spring Data types, and snapshot/retention services reuse AlarmView from the API DTO package. It does not claim a framework-independent domain or fully hexagonal architecture.

03 | Ingestion and alarm-state lifecycle

  1. Admit the request and bound POST-body size and upload time.
  2. Parse and validate required fields, identifiers, enums, timestamp and description.
  3. Start a transaction, acquire the event-ID lock and check its receipt or legacy history.
  4. For a new event, acquire the element lock, validate the transition, insert history and check lifetime capacity.
  5. Insert the duplicate receipt and create, update or remove active state.
  6. Commit before returning a newly accepted acknowledgement.
Current stateEventResult
AbsentUnique RAISEDAppend history and create active state.
ActiveUnique RAISEDAppend history and update the active event reference.
ActiveUnique CLEAREDAppend history and remove active state.
AbsentUnique CLEARED409; no new accepted history or receipt.

An old raise replay cannot resurrect a cleared alarm. A clear replay still succeeds after the original transition removed active state. A rejected unknown clear does not permanently reserve its event ID.

04 | Concurrency, ordering and duplicate identity

Exact database keys

New-event transactions acquire event:EVENT_ID, then element:ELEMENT_ID in ingestion_key_lock. Parameterized INSERT ON CONFLICT DO NOTHING safely creates absent keys; SELECT FOR UPDATE holds their row locks until commit/rollback. JDBC locks and JPA changes participate in the same Spring transaction and datasource connection.

The event key protects global uniqueness, including one ID reused across different elements. The element key serializes updates for all alarm codes on that element, including first raises for absent state. Different IDs on different elements proceed independently, subject to the shared pool and admission limits. Exact strings avoid hash-stripe collisions.

Acceptance order

Ordering is successful processing order within an element, not socket arrival, FIFO fairness or producer timestamp. Older/equal timestamps still take effect when accepted later. Identity IDs reflect allocation order and may contain rollback gaps; they do not imply global commit order across different elements.

Identity after archival

A receipt stores event ID, original history ID and a SHA-256 fingerprint of a fixed-order JSON array containing every accepted payload field. Escaping and explicit nulls avoid concatenation ambiguity. Incoming JSON property order is irrelevant. Omitted/null description are equivalent; empty text differs.

Legacy receipts are backfilled on replay or archival. Retention takes the same event keys before receipt creation and deletion so legacy replay cannot race the transfer. The old singleton ingestion_lock now coordinates only snapshot quota and retention; it is not an ingestion mutex.

Event/element IDs are 1–128 characters; alarm codes are 1–64. Identifiers are case-sensitive, untrimmed ASCII [A-Za-z0-9_.:-]. Required severity/status values are uppercase enum strings. Timestamp is a required nonnegative signed 64-bit epoch-millisecond integer; no wall-clock or future-date restriction applies.

Description is optional/nullable, at most 2,048 characters, and rejects NUL. Jackson rejects unknown properties, duplicate keys, trailing JSON, scalar coercion, numeric enum values and floating-point timestamp tokens. Page defaults to 0 and ranges to 1,000,000; size defaults to 100 and ranges from 1 to 500.

07 | Stable pagination

Page zero without a token creates a database snapshot. Under maintenance quota coordination, the service checks capacity, runs one bounded SELECT, maps events to response DTOs, enforces encoded size and stores the frozen list. Total count is the list length, avoiding a second count query that could observe different state.

GET /api/alarms/history?elementId=BTS-102&size=20
Response: {content, page:0, size:20, totalElements, snapshotId, expiresAt}

GET /api/alarms/history?elementId=BTS-102&size=20&page=1&snapshotId=UUID

Later pages slice that same payload and must use the same endpoint kind and element filter. Tokens work across instances sharing PostgreSQL. New events, clearing and archival cannot change an existing snapshot. A new snapshot is required to refresh active state.

Later page without a token or query mismatch: 400. Expired/missing token: 410. Too many matching records/encoded bytes: 413. Exhausted snapshot count: 429. Expiry cleanup runs during creation and maintenance. A token is an unpredictable result identifier, not an authenticated access credential.

08 | Retention, archives and finite capacity

Archive-before-delete

Maintenance starts after one minute and processes at most 500 records per run, with a one-minute delay after completion. Default age is over 30 days by server acceptance time. Producer timestamps cannot force early pruning. Active-state history references are excluded.

The service selects candidates under maintenance coordination, acquires event keys, ensures receipts and writes compressed JSON Lines to a temporary file. It closes the stream, checks capacity, forces file contents to storage and atomically renames the archive before deleting database rows in its transaction.

Filesystem/database boundary: file publication and database commit are separate. A crash between them can leave an extra export; consumers must deduplicate by event ID. This is not exactly-once export or protection against storage-media loss.

Archive failure or full capacity preserves live history and logs an operator-action error. File-count and compressed-byte budgets include incomplete crash files. Operators must offload verified backups and back up both volumes. The HTTP history endpoint lists retained database payloads; older payloads are available to operators in archives.

Permanent identity with bounded admission

Permanent global deduplication needs permanent identity storage. A configurable lifetime history-ID ceiling bounds it. The service checks the atomically allocated ID before committing; an above-ceiling request returns 507 and rolls back history, receipt and state. This avoids serializing unrelated elements on a global transactional quota counter.

Rollback attempts consume sequence values, making the ceiling conservative rather than a precise event count. Archival does not free IDs. Duplicates remain replayable at capacity. Operators may deliberately raise capacity after sizing storage; live sequences must never be reset to reuse identities.

09 | Security boundaries: implemented and absent

Implemented controls

  • Typed input validation and strict JSON parsing.
  • Body, snapshot, upload and admission bounds.
  • Parameterized JPA/JDBC access.
  • X-Content-Type-Options: nosniff and Cache-Control: no-store.
  • Custom error responses and logs omit raw SQL, credentials and submitted payloads.
  • Loopback host publication, internal database network and unprivileged container.
  • Database password supplied through environment configuration.

Not configured

  • Spring Security dependency or security filter chain.
  • Authentication, authorization or element-scoped permissions.
  • CSRF protection, sessions or a CSRF-token endpoint.
  • Custom CORS policy or @CrossOrigin declarations.
  • TLS termination, HSTS, CSP or frame-protection policy.
  • Distributed rate enforcement or a separate restricted runtime database role.

This is a trusted-local synthetic-data service. Cross-origin JavaScript receives no application-configured CORS permissions; CORS does not restrict non-browser callers or replace authorization. A future HTML client must escape descriptions. Public deployment requires an explicit security design and authenticated HTTPS ingress. The Compose database role also owns schema/migration privileges for convenience.

A multi-stage Docker build compiles with Maven/Java 17, then copies the executable JAR into a Java runtime image. Compose waits for database health before app startup. Standalone binding defaults to loopback; the container listens on its internal interfaces while host publication remains loopback-only.

DB_PASSWORD is required. DB_URL, DB_USER and SERVER_ADDRESS configure standalone execution. Compose forwards MAX_HISTORY_ID, HISTORY_RETENTION_DAYS and MAX_ARCHIVE_BYTES. Archive location is /archives in Docker and ./archives locally.

V2 adds exact-key locks, acceptance time, receipts and snapshots without deleting V1 history. Existing rows receive migration-time acceptance age; receipts are backfilled lazily. Stop all V1 writers before V2 starts because their locking protocols differ. V2 replicas must share PostgreSQL and consistent capacity settings; shared archive storage is required for a common archive budget.

No application readiness endpoint, production HA setup, automatic backup restore or deployment TLS is included. See the operations guide for startup, upgrades, capacity and recovery.

13 | Verification evidence and practical limits

The recorded implementation passed 21 automated tests on H2 and PostgreSQL 18.3, covering lifecycle, replay, competing writers, snapshots, retention, filesystem failure, quotas, parsing, error classification and admission. A separate harness passed 25 actual HTTP/database checks with two application processes.

The harness exercised cross-instance deduplication, blocked-element isolation, lost responses, application kill during insertion, immediate restart of an isolated PostgreSQL cluster, scheduled archives, idle/trickled uploads, burst overload and capacity rejection. Temporary processes were stopped after verification.

Docker was separately built/migrated against PostgreSQL 17.11, with browser checks for history responses and fractional-timestamp rejection. This is a startup/migration smoke check, not the full suite on PostgreSQL 17. Recreating this document does not change backend behavior or repeat earlier application tests.

See validation evidence and harness instructions. Remaining scope includes authentication/authorization, optional notifications, sustained load benchmarks, production observability, archive restore drills and authenticated public ingress.
