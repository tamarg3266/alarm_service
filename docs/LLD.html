1. Types and dependency boundaries

com.septier.alarms
  AlarmApplication
  api: AlarmController, dto/AlarmView, error/ApiErrors
       filter/RequestSizeFilter, RequestAdmission, UploadConfiguration
  application: AlarmService, EventFingerprint, QuerySnapshots
               HistoryRetention, RetentionScheduler
       command/AlarmRequest
  domain: model/AlarmEvent, ActiveAlarm, Severity, AlarmStatus
          exception/AlarmConflict, ApiFailure
  infrastructure/persistence: AlarmHistoryRepository, ActiveAlarmRepository
       KeyLocks, EventReceipts, IngestionLock, IngestionLockRepository

AlarmController adapts HTTP only. AlarmService coordinates atomic acceptance, exact-key locks and duplicate receipts. QuerySnapshots persists bounded read results. HistoryRetention handles export/delete and RetentionScheduler invokes it through the Spring transactional proxy. KeyLocks uses JDBC on the transaction-bound datasource connection, so its locks participate in the same JPA transaction. No independent lock connection or process-local state protects persistence.

EventFingerprint serializes a fixed-order array of all accepted fields and hashes UTF-8 JSON with SHA-256. JSON escaping and explicit null array entries avoid concatenation ambiguity. Absent/null description compare alike; empty string differs. Receipt insertion verifies an existing conflict matches both history ID and fingerprint instead of silently hiding inconsistent identity.

3. Ingestion transaction

@Transactional(timeout=10)
  lock exact event ID (insert-if-absent, SELECT FOR UPDATE)
  fingerprint the validated command
  if receipt exists:
    same fingerprint -> original ID, duplicate=true
    different fingerprint -> 409
  if legacy history exists:
    compare canonical fingerprint; backfill receipt; return duplicate
  lock exact element ID
  read active key
  unknown CLEARED -> 409, rollback
  insert and flush history (identity allocation)
  allocated ID above configured ceiling -> 507, rollback
  insert receipt, verifying any conflicting existing row
  RAISED -> insert/update active pointer; CLEARED -> delete pointer
  commit before returning 201

All writers use event then element order. A request holds only one event key and one element key. Same element events serialize across instances, while different elements can commit independently. Identity IDs can have rollback gaps and cross-element commit inversions. Retention may hold several event keys but never element keys; maintenance serialization prevents two archive workers acquiring different event batches in reverse order.

PostgreSQL lock_timeout=5s, statement_timeout=10s and transaction timeout=10s bound storage waits. Hikari has ten connections and three-second acquisition timeout. The transaction bounds are not whole-HTTP deadlines.

4. Stable query protocol

GET /api/alarms/history?elementId=BTS-102&size=20
  -> {content, page:0, size:20, totalElements,
      snapshotId:UUID, expiresAt:ISO8601}
GET /api/alarms/history?elementId=BTS-102&size=20&page=1&snapshotId=UUID

Active and element endpoints use the same contract. Query identity includes endpoint kind and element filter. At page zero without a token: lock the maintenance quota row, remove expired snapshots, check max count, load a bounded single-query result (maxRecords+1), map to AlarmView, enforce record and encoded-byte limits, then insert token/payload/expiry atomically. TotalElements is the stored list length, not a second count query.

At token reads: fetch the persisted payload, validate expiry and query identity, deserialize, and slice using a long offset calculation. Page and size input remain bounded. A token may be served by any replica. Snapshot reads do not need the quota lock. Expired payloads are reclaimed during creation and scheduled maintenance. Frozen active records can remain visible after a later clear until the client refreshes.

Errors: missing token on later page 400; wrong query 400; expired/unknown 410; result/byte cap 413; snapshot count cap 429. UUID tokens offer unpredictability, not access control. Limits: 120 seconds, 32 snapshots, 10,000 records and 4 MiB. This bounds database payload storage and materialization memory, with temporary object overhead beyond encoded bytes.

5. Retention and capacity algorithm

@Transactional(timeout=30, rollbackFor=Exception)
  acquire maintenance row; prune expired snapshots
  SELECT old, inactive history IDs
    ORDER BY id LIMIT batch FOR UPDATE SKIP LOCKED
  check archive file count and byte budget
  create temporary file on the destination filesystem
  for each record:
    acquire its event key; ensure canonical receipt
    write full AlarmView as a JSON line through GZIP
  close compressed stream; enforce final compressed byte budget
  fsync temporary file; atomic rename to history-UUID.jsonl.gz
  delete selected database history; commit

Age uses server accepted_at; producer timestamps cannot force early pruning. Selection excludes all active foreign-key references. Atomic rename must be supported; failure rolls back and retains live rows. A failed database commit after rename leaves a harmless duplicate export. A crash before rename may leave a temporary file; it counts toward capacity and requires operator inspection. Archive consumers deduplicate by eventId. No unverified export is treated as permission to delete the sole payload copy.

Receipts and exact-key rows cannot be removed while global event IDs must remain unique. MAX_HISTORY_ID uses sequence allocation to cap their lifetime cardinality without serializing every transaction on a quota row. Above-ceiling allocation rolls back and returns 507. Failed transactions burn IDs; operators raise the ceiling only after storage sizing. Default archive budget is 1 GiB and 10,000 files; default batch is 500 every minute after 30 days. Archive storage must be shared across replicas and backed up with the database.

6. HTTP admission, parsing and upload deadlines

RequestAdmission uses a semaphore for 32 simultaneous requests and a synchronized, bounded token-bucket map keyed by actual socket peer. Each peer receives 30 tokens/second and burst 120; the map holds at most 1,024 buckets and removes entries idle for two minutes. It does not trust forwarded headers. All admitted paths release permits in a finally block. Rejections return 429 and Retry-After: 1.

RequestSizeFilter reads POST bodies in at most 1,024-byte chunks with a 16,385-byte detection ceiling. It checks monotonic elapsed time before and after every read, returns 413 above 16 KiB, and returns 408 on deadline/read failure. Tomcat enables connectionUploadTimeout and disables its default upload-timeout exemption. A five-second idle/read timeout bounds the final blocked read, making total upload time approximately at most ten seconds plus scheduling/network overhead. A bounded byte-array wrapper supplies synchronous MVC input.

Jackson disables ACCEPT_FLOAT_AS_INT, scalar coercion and enum ordinals, and enables unknown-field, duplicate-key and trailing-token rejection. Timestamp must be a nonnegative Long; decimal/exponent-float tokens are rejected. Description rejects NUL before PostgreSQL and is at most 2048 characters. IDs remain case-sensitive ASCII identifiers with 128/64 bounds. These are resource and syntax checks, not authentication or a distributed rate limiter.

7. Error classification

StatusMeaning
400 / 409Request validation / alarm or integrity conflict. No unconditional retry advice.
408 / 413 / 429Upload deadline / size cap / request or snapshot admission.
503 + Retry-AfterTransient Spring exceptions or nested SQL states: 08 connectivity, 40 transaction rollback, 53 resource shortage, 55P03 lock timeout, 57014 cancellation, 57P01/02/03 shutdown/recovery.
500Other storage/transaction errors; operator investigation. No Retry-After.
507Lifetime identity capacity exceeded; explicit operator action.

PostgreSQL native lock timeout can surface as UncategorizedSQLException, so classification inspects nested SQLState instead of trusting the Spring exception family alone. Commit disconnects may wrap SQL exceptions in TransactionSystemException. Messages and logs avoid private SQL and submitted data. Unknown outcome recovery always reuses the original event ID.

8. Verification and operations

Regression tests cover transitions, rejected events, original replay semantics, archive/replay and legacy backfill, filesystem failure, frozen pages, expiry and caps, lifetime capacity rollback, fractional/NUL rejection, admission boundaries, SQLState classification and synchronized competing writers. Test identities and rows are reset only in disposable databases.

tools/e2e.py starts two actual Java processes, sends HTTP requests, inspects PostgreSQL, holds per-element locks, discards responses after commits, kills a JVM during an insert and optionally immediately restarts a dedicated test cluster during a transaction. It also verifies scheduled archive files, stalled/trickled socket uploads, burst 429 responses and capacity rejection. It creates a unique alarm_e2e_* database and retains evidence under .tools.

See executed validation for versions/results and operations for migration, capacity sizing, backup, snapshot usage and harness prerequisites. Public ingress authentication/TLS, notification workers, sustained load benchmarks and backup restore drills are not implemented by this change.
